# TechJam2026 Shopping Copilot - Conversational Search & Recommendation Agent

A complete engineering implementation for the TechJam2026 "Shopping Copilot: AI Conversational Search & Recommendation" competition,
built on the frozen toolkit (Amazon Reviews 2023 `Clothing_Shoes_and_Jewelry`: 50,000 products / 200 public dev sessions / 800 private evaluation sessions).
**The official evaluator is never modified**; the official Python Agent interface and the machine-readable API contract are fully respected.
The default config runs with zero external dependencies and clearly beats the weak BM25 baseline on the public set.

| Metric | Weak BM25 baseline | This project (public 200, default adaptive config, offline) |
|---|---|---|
| Hit Rate@10 | 0.125 | **1.0** |
| MRR | 0.0680 | **0.9364** |
| MTTC (avg turns to conversion) | 9.81 | **2.33** |
| Efficiency | 0.119 | 0.867 |
| TechnicalScore | 0.1067 | **0.9543** (full 200 measured; train160 0.954 / holdout40 0.955) |

> Reproduce: `python run_local_eval.py` (default ENV_MODE=dev / LLM_PROVIDER=deepseek; offline when no key is set / RETRIEVAL_BACKEND=bm25).

## 1. Project overview & four-pillar mapping

### Pillar I | Core architecture: intent routing & hybrid pipeline
- **Dual-track intent routing** `agent/intent_router.py`: detects a high-intent buying track (hard constraints -> high-precision constraint filtering)
  versus an open browsing track (no constraints / over-general -> diverse generalized recall), switching dynamically with session state.
- **Multi-route hybrid retrieval** `agent/retriever.py`:
  - BM25 route: SQLite FTS5 with multi-field weighting (title/features get the highest weights);
  - Category route: filters by category-domain hits;
  - Hard-constraint AND route: index-level FTS "AND" over hard-constraint token groups (guarantees must-hit candidates enter the pool; raises HitRate@K);
  - **BLaIR dense route** (`RETRIEVAL_BACKEND=dense/hybrid`, recommended): product vectors are **pre-computed offline** by
    `scripts/encode_catalog_blair.py` (`hyp1231/blair-roberta-large`, CLS pooling + L2, output `data/offline_blair_embeds.npy`, 1024 dims);
    at inference only the user query text is encoded (`utils/blair.py`) and dot-product recall runs against the full-catalog vectors.
    **Mode-adaptive**: enabled only in `recover` (miss streak needs broader recall) + hard-constraint coverage re-check + 0.5 weight -- under
    probe/exploit, semantic candidates disturb the aligned rule order (A/B verified); missing encoder (transformers) or offline npy -> auto-fallback to BM25.
  - Fusion: Reciprocal Rank Fusion (RRF).
- **Field-aware structured filtering** `data/analysis/field_mapping.json` (generated by `scripts/build_field_mapping.py`):
  attribute -> where to look (lookup_fields + weights) + filter strictness (tolerance/missing_policy). material looks up
  details.Material/features/title; budget only checks price (79% missing -> pass); brand checks store (missing -> pass).
  `retrieval_pipeline` channel 1 integrates it; A/B shows the reranker keeps full-text scoring as optimal (pure-field/layered scoring drops MRR,
  see the "override design" section).
- **Reranking** `agent/reranker.py`: rule fusion scoring (constraint coverage 0.5 / **combo_bonus 0.10** / category 0.25 / RRF 0.15 /
  popularity 0.05 / profile 0.05) -- combo_bonus gives a C(n,2)/C(N,2) super-linear bonus to products "fully hitting >=2 disclosed constraints"
  (the hidden target comes from its own metadata, naturally a full hit; this lifts MRR) + optional **qwen3-rerank text rerank**
  (`LLM_RERANK=1` + `LLM_RERANK_BACKEND=text`, Alibaba Cloud MaaS `/reranks`, `DASHSCOPE_API_KEY` injected; auto-fallback on failure);
  + optional local **reranker models** (`RERANKER_MODEL_ENABLE=1`, dispatched by `RERANKER_MODEL`: `thebajajra/RexReranker-0.6B` /
  `Qwen/Qwen3-Reranker-*` use generative yes/no scoring, `BAAI/bge-reranker-v2-m3` uses FlagEmbedding cross-encoding; failure falls back to rules).
  Default `LLM_RERANK=0` / `RERANKER_MODEL_ENABLE=0` keeps pure rule ordering, fully offline.

### Pillar II | Dialogue strategy: multi-turn scenario evolution (dialogue pipeline `agent/dialogue/`)
- **Recognition layer** `agent/dialogue/recognizers/`: cascaded intent recognition (rules first + strict-JSON LLM fallback),
  producing `DialogueAct` (new_search / add_constraint / replace_constraint / remove_constraint / reject_products /
  no_preference / no_more_preferences / ambiguous) and `ConstraintOperation` (polarity include/exclude, strength hard/soft, evidence, confidence).
- **State reduction** `agent/dialogue/reducer.py`: the only component allowed to produce new `DialogueState` -- incremental slot accumulation +
  sudden-intent override (REPLACE / NEW_SEARCH clear old constraints and bump `intent_version`; by default old preferences stay as weak soft signals,
  `OVERRIDE_ERASE=1` switches to aggressive erasure).
- **Proactive clarification** `agent/dialogue/question_policy.py` + `catalog_signals.py`: catalog-aware ask-utility scoring and stop policy --
  `ask_other_first` by default ("other" shrinks the candidate pool from 4930 to 307 per turn on average while keeping a 0.99 hit rate;
  data-validated optimal); candidate overflow / insufficient info -> `ask_attribute` to converge; utility saturation / customer "no more preferences" ->
  STOP-ASK, avoiding redundant turns and optimizing MTTC.
  Each attribute has 4-5 phrasing templates: `decision.question_template_mode=random` (default) picks pseudo-randomly by (session_id, turn, attribute)
  with no consecutive repeats -- demos look natural and stay reproducible; `rotation` keeps the legacy deterministic rotation;
  the phrasing never affects `ask_attribute` or official scoring.
- **Product feedback loop** `agent/dialogue/product_history.py`: versioned product display/feedback tracking
  (hard_rejected / soft_demoted -> excluded/down-weighted in the next turn's retrieval).

### Pillar III | Self-evolution: dynamic context programming
- **Runtime context distillation** `agent/dialogue/pipeline.py::_build_context`: each turn compiles `DialogueState` + recognition +
  `ProductHistory` into a `RecommendationContext` (constraints / category / intent track / retrieval mode probe-exploit-recover / asked attributes /
  excluded & down-weighted products), which downstream `intent_router -> retriever -> reranker` "recompiles" to execute;
  the long-term user profile is only a weak prior (in-memory, never persisted).
- **Adaptive orchestration**: computes `probe / exploit / recover` retrieval modes from state; `IntentRouter` downgrades hard groups to soft in RECOVER;
  `RuntimeController` autonomously decides whether to enable LLM/dense/rerank from the capability probe -- **no model training**,
  pure context programming for policy adaptation.

### Pillar IV | Evaluation-matrix alignment
- Metric-facing design: hybrid retrieval protects **HitRate@K** recall; reranking (full-coverage bonus + rule fine-ranking) pushes the target up for **MRR**;
  proactive clarification + stop policy lower **MTTC**. All metrics are computed by the official evaluator; this project only adapts the agent side.

## 3. Unified LLM provider configuration & availability

Configuration is no longer direct environment-variable parsing. General settings merge in four layers, low to high:

1. built-in `AppConfig` defaults;
2. the versioned non-secret file `config/default.json`;
3. environment variables;
4. explicit runtime overrides passed to `load_config(..., overrides=...)`.

The default JSON file can be redirected with `APP_CONFIG_PATH`; a path passed directly to `load_config(path=...)` takes priority over `APP_CONFIG_PATH`.
Credentials may only come from the selected provider's `DEEPSEEK_API_KEY` or `OPENAI_API_KEY`; they cannot be written into JSON or explicit overrides,
and they never appear in the config summary, startup output, or error text.

| Variable | Default | Description |
|---|---:|---|
| `ENV_MODE` | `dev` | local dev, or `submit` submit-simulation (forces offline constraints) |
| `LLM_BACKEND` | unset | compatibility mapping: `none/local -> none`, `openai -> openai`; `LLM_PROVIDER` wins when set |
| `RETRIEVAL_BACKEND` | `bm25` | `bm25` / `dense` / `hybrid` / `auto` (auto: dense available -> hybrid, else bm25) |
| `TOP_K` | `10` | recommendation count K |
| `APP_CONFIG_PATH` | `config/default.json` | location of the non-secret JSON config file |
| `DEEPSEEK_API_KEY` / `OPENAI_API_KEY` | empty | only the selected provider's matching key takes effect; no network request when unset |
| `LLM_PROVIDER` | `deepseek` | unified provider: `none` / `deepseek` / `openai` |
| `DEEPSEEK_MODEL` / `DEEPSEEK_BASE_URL` | see JSON | DeepSeek profile overrides |
| `OPENAI_MODEL` / `OPENAI_BASE_URL` | see JSON | OpenAI profile overrides |
| `LLM_MODEL` / `LLM_BASE_URL` | see selected profile | override only the selected provider's model / base URL |
| `LLM_HEALTH_CHECK_ENABLED` | `true` | whether to send a lightweight availability probe at startup |
| `LLM_CONNECT_TIMEOUT_SECONDS` / `LLM_TIMEOUT_SECONDS` | `3` / `8` | connect / request timeouts (s) |
| `LLM_MAX_RETRIES` | `2` | extra retries for probeable failures (at most 3 startup requests) |
| `LLM_RETRY_BASE_DELAY_SECONDS` / `LLM_RETRY_MAX_DELAY_SECONDS` | `0.5` / `1.5` | retry backoff range (s) |
| `LLM_CIRCUIT_BREAKER_FAILURE_THRESHOLD` | `2` | runtime failure threshold before opening the circuit breaker |
| `LLM_INTENT_ENABLE` | `0` | use the LLM for intent recognition (off by default; truly enabled only when probed available; rule fallback on failure) |
| `LLM_INTENT_JSON_OUTPUT` | `1` | request provider-supported JSON output for intent recognition |
| `LLM_INTENT_THINKING_MODE` | `disabled` | DeepSeek intent-call thinking mode: `default` / `disabled` / `enabled` |
| `LLM_INTENT_NORMALIZATION_VOCAB` | `1` | provide catalog-supported English canonical values for Chinese intent normalization |
| `LLM_INTENT_NORMALIZATION_MIN_PRODUCT_COUNT` | `1` | minimum catalog support required before a canonical value is exposed to the LLM |
| `LLM_CLARIFY_ENABLE` | `0` | use the LLM for clarify decisions (off by default; same semantics) |
| `CAPABILITY_NETWORK_PROBE` | `0` | additionally probe external connectivity when the LLM is unavailable (1=on, httpx 2s) |
| `EMBEDDING_MODEL` / `RERANKER_MODEL` | see `config/default.json` | optional retrieval and rerank models |
| `CLARIFY_STRATEGY` / `OVERRIDE_ERASE` / `LLM_RERANK` | `other` / `0` / `1` | dialogue policy; `LLM_RERANK=0` forces deterministic rule rerank |
| `SAMPLE_LIMIT` / `SKIP_DATA_VERIFY` / `OUTPUT_PATH` | empty / `0` / `results.json` | smoke scope, data verification, and result path |

Chinese-containing intent requests keep the existing English JSON contract. Closed attributes
(`category`, `material`, `color`, `size`, `style`, and `use_case`) receive canonical values from
`data/assets/vocab_v2_clean.json`, filtered by catalog `product_count`; Chinese is preserved only in
the grounded `evidence` span. Open attributes such as `feature`, `brand`, and `other` remain free-form.

Every `run_local_eval.py` startup prints the sanitized LLM state before data verification: provider, model, state, attempts, and the error category when available:

- `disabled`: no key or provider `none`; no SDK construction or network access.
- `available`: SDK ready and the health check succeeded; with health check off, this state is reachable without sending a probe request.
- `unavailable`: the probe failed, but evaluation never raises because of it; the output only shows a category (e.g. `timeout`), never credentials.

The unified client is injected at startup (one provider, one shared client). There is no automatic DeepSeek-to-OpenAI fallback and no local-model implementation;
missing selected credentials leave the client offline. The Reranker sends at most 12 candidates by default; empty/malformed output falls back to the complete
deterministic rule order. `LLM_RERANK=0` is a deterministic opt-out even with an available key.

### Environment awareness & autonomous decisions (team highlight)

At startup the agent runs a one-time **capability probe** (`agent/capability_probe.py`), then the **autonomous decision controller**
(`agent/runtime_controller.py`) decides how each stage executes from the probe + config, printing:

```
[capability] device=cpu llm=deepseek:disabled dense=yes reranker=yes network=no
[decisions ] retrieval=bm25 intent=rule clarify=rule rerank=rule reranker_model=no
```

- **Probed items**: device (cuda/cpu), LLM availability (real health check; no network request without a key),
  dense retrieval (BLaIR query encoder importable from transformers/sentence-transformers **and** the offline product-vector npy exists),
  cross-encoder rerank (FlagEmbedding importable + bge-reranker-v2-m3 cached/downloadable),
  **text rerank qwen3-rerank** (real `/reranks` probe with `DASHSCOPE_API_KEY` + the international endpoint), optional external-network probe.
- **Autonomous-decision principle**: all LLM/rerank capability switches are **off by default**; config on + probe available -> enabled;
  config on but environment unavailable -> **auto rule fallback** (intent/clarify/rerank/dense all fall back);
  `RETRIEVAL_BACKEND=auto` -> hybrid when dense is available, else bm25.
- **BLaIR dense-channel robustness (environment awareness)**:
  - missing/dimension-mismatched offline npy -> `BlairEmbeddingStore.load` returns None -> dense channel disabled;
  - query-encoder load failure -> tries sentence-transformers fallback, then disables;
  - any exception is caught by `_route_dense` and only affects the dense route, never the BM25/category/constraint main flow.
- **LLM intent recognition** (`agent/dialogue/recognizers/llm.py`): the cascade consults the LLM on low rule confidence / ambiguity / replace;
  (strict JSON; failure/invalid output always falls back to rules); **LLM-extracted constraints are only soft retrieval terms** (protecting hard filters from hallucination).
- **Clarify decisions always use the rule policy** (`ask_other_first`, data-validated optimal), never the LLM.
- Timeouts (connect 3s / total 8s) and circuit breaking (2 failures) are guaranteed by the unified LLM client; an LLM failure never blocks the main flow.

### Offline loading
- **Reuse the HF cache** (default): `snapshot_download` writes to `~/.cache/huggingface/hub/`; transformers/FlagEmbedding read it automatically.
- **Custom local_dir**: after downloading to a custom directory, point the env var at it:
  - BLaIR query encoder: `BLAIR_QUERY_ENCODER_MODEL=hyp1231/blair-roberta-large` (or the local absolute path);
  - rerank model: `RERANKER_MODEL=BAAI/bge-reranker-v2-m3` or `RERANKER_MODEL=/path/to/RexReranker-0.6B`.
- BLaIR product vectors (`data/offline_blair_embeds.npy`, 204MB) are produced once by `python scripts/encode_catalog_blair.py`
  (GPU ~25min / CPU ~6h) and ship with the data package; when missing, the dense channel auto-disables.

### Submission strategy & fallback
- **Large models are not bundled** (`*.npy` and HF caches are gitignored); the deliverables are: code + frozen data +
  data assets (`data/assets/`) + lightweight analysis artifacts (`data/analysis/`) + this install/download guide.
- At deploy time, run `pip install` + `snapshot_download` from this section to reproduce all capabilities.
- **Missing-model auto-fallback**: when a dependency/cache is not detected, capability_probe reports `dense=no / reranker=no` and
  RuntimeController falls back to `strategy=bm25_rule` (the safe offline path).

## 5. Limitations & next steps

### Known limitations
1. The agent leverages the deterministic simulator wording; if the private set introduces natural-language paraphrases, rule recognition degrades.
   Hard-cue upgrades + cascaded LLM + the review_paraphrase asset + the rewrite guard mitigate this (stress-tested by `tools/paraphrase_eval.py`).
2. The user profile carries little information on the public set (weak prior only); a more discriminative private profile could be re-weighted.
3. Semantic reranking mismatches the deterministic evaluator mechanics (A/B proven), so it stays an optional enhancement.
4. The public 200 sessions and private 800 may differ in difficulty distribution; the LUT is measured on public data and needs recalibration.
5. LUT latency is measured on this machine; absolute CPU/cloud latency differs (relative ordering holds).

### If we had more time
- **Recalibrate the LUT for the private set**: the LUT is measured on the public 200; a private-800 run would retrain the
  environment-to-config table so startup selection matches the real difficulty distribution.
- **Adversarial auto-tuning**: replace manual A/B with an automated opponent loop that mines worst-case messages (paraphrases,
  partial overrides, ambiguous mentions) and tunes the dialogue/retrieval knobs against them.
- **Cross-session profile learning**: the long-term profile is currently a weak prior; learning richer per-user preference
  vectors across sessions could help when private profiles are more discriminative.
- **Cheaper/faster dense path**: distill or quantize the BLaIR encoder and pre-computed vectors so hybrid retrieval is practical
  on CPU-only submission machines.
- **Latency profiling on reference hardware**: publish measured latency for cpu-only and cloud environments, not just this GPU laptop.

## Optimization record (2026-08-30; public-200 A/B + 40-session holdout)

| Config | train(160) TS | **holdout(40) TS** | Note |
|---|---|---|---|
| baseline (no gating / no fingerprint) | 0.882 | 0.894 | -- |
| + fingerprint (combination rarity) | -- | -- | exact catalog count of products satisfying all constraints; smaller count = rarer -> tiered top placement |
| + output gating K0=1/K1=1/K2=1/late=5 | 0.954 | **0.955** | low-confidence hold-back: 0/1/>=2 constraints emit 1/1/1; full capacity at turn>=5 or high confidence |
| + confidence gating | 0.954 | 0.955 | fp uniqueness<=3 / top margin>=0.10 / constraints>=4 -> release early (avoid wasting turns) |

- Default config (default.json): `fingerprint.enable=true`, `emit_gate=true`, `emit_k0=1`, `emit_k1=1`, `emit_k2=1`,
  `emit_late_turn=5`, `emit_fp_confident=3`, `emit_margin_confident=0.10`, `emit_commit_constraints=4`.
- **40-session holdout**: tuning (160) and holdout (40) both ~0.955 with HR=1.0 -- not pure public overfitting.
- Mechanism: a hit locks the rank -> emit less at low confidence, full capacity at high confidence / late turn, deferring early low-rank hits to a confident rank-1.

### Paraphrase robustness (private 800 unknown + possible rewrites)

Using `tools/paraphrase_eval.py`, customer messages are rewritten (L1 template rewrite / L2 value-synonym rewrite) and 200 sessions replayed:

| Config | No rewrite | L1 template rewrite | L2 value-synonym rewrite |
|---|---|---|---|
| rules only | 0.955 | **0.383** (collapse) | 0.383 |
| rules + LLM intent (DeepSeek, 40 sessions) | -- | **0.886** | 0.886 |

**Conclusion & disclosure**:
- The rule recognizer is optimal for official templates but **fragile under natural-language rewrites** (template set optimal; rewrite -> collapse);
- **LLM intent recognition (cascaded) is the necessary robustness lever for a rewritten private set** (0.38 -> 0.89); on the public template set it does not help
  (even slightly hurts), so it is off by default and enabled automatically by the automation control (LUT/controller) when the LLM is available (`hybrid_llm_intent`);
- Final scoring: if offline, templated messages -> rule default ~0.955; if rewritten, rules degrade and the LLM needs network (disclosed in the submission notes).

## Dialogue understanding pipeline (agent/dialogue/)

The dialogue pipeline is the team-fused module that drives Pillars II/III: a cascaded recognizer (rules first, strict-JSON LLM fallback),
an atomic reducer with intent_version versioning (override semantics: "ignore my earlier preference" keeps old preferences as weak soft signals,
with `intent_version` bumped; `OVERRIDE_ERASE=1` switches to aggressive erasure), a catalog-aware question policy with ask/stop utilities
(ask_other_first by default), and a versioned product-history feedback loop. All session state is in-memory and never persisted.

## field_mapping static table + override design (data-driven A/B)

### field_mapping.json (attribute -> where to look + how strict)

A static table mapping each attribute to lookup fields, weights, and filter strictness (tolerance/missing_policy), produced by
`scripts/build_field_mapping.py` from `data/analysis/stats.json` + per-field coverage statistics. It answers: "for a user constraint
{material: cotton}, which catalog fields should be searched for 'cotton', and does a miss mean the constraint is unmet?"
material looks up details.Material/features/title (a hit on the authoritative key is high confidence); budget only checks price
(79% missing -> pass, never a hard filter); brand checks store (missing -> pass). Consumers: agent/reranker.py constraint-hit scoring,
agent/retriever.py structured filtering, and retrieval_pipeline channel 1.

### override (intent override) design -- task semantics + data validation

- Official template "ignore my earlier preference..." -> `DialogueAct.REPLACE` / `NEW_SEARCH`; the reducer clears old hard constraints and
  bumps `intent_version`.
- **Conservative default**: old preferences downgrade to weak soft signals and stay, because the hidden target usually satisfies both old and new
  constraints (28 of 30 sessions in a manual check); dropping them would lose ranking signal (A/B: MRR 0.769 -> 0.744).
- Synonym expansion is gated by intent_version in intent_router and stops after an override, so old-preference terms never pollute the new query.
- `OVERRIDE_ERASE=1` switches to aggressive erasure for teams that prefer that semantics.

## qwen3-rerank text-rerank integration (replaces the LLM semantic-rerank branch)

`llm/rerank.py` implements a real text-rerank client (Alibaba Cloud MaaS `/reranks`): model `qwen3-rerank`, key only from `DASHSCOPE_API_KEY`,
base_url from `QWEN_RERANK_BASE_URL` (full) > `DASHSCOPE_WORKSPACE_ID` subdomain > the international default endpoint. Three-state availability:
available / disabled (no key or base_url) / unavailable (probe failure). Failures/timeouts always return None -> the caller falls back to rule ordering.

### Real-API full-200 A/B

| Config | MRR | TS | Note |
|---|---|---|---|
| rule rerank (default) | 0.9364 | 0.9543 | offline, zero cost |
| + qwen3-rerank as final rerank | drops | drops | semantic ordering mismatches the deterministic evaluator; optional only |

Conclusion: qwen3-rerank text rerank is wired and tested, but as the *final* reranker it hurts MRR on this evaluator (same as bge/Rex),

## RexReranker-0.6B e-commerce rerank model deployment (A/B vs bge-reranker-v2-m3)

`utils/rex_reranker.py` implements the generative rerank scorer (chat template + assistant suffix; score = exp(yes)/(exp(yes)+exp(no))),
dispatched by model name in `agent/reranker.py::_ensure_reranker_model`. `RERANKER_MODEL_ENABLE=1` runs it only in recover mode as a
"second opinion" over Top-50. A/B: full/recover enablement both slightly hurt MRR on the public set (same conclusion as bge), so it stays off by default.

## Default strategy: environment-adaptive optimum (never permanently pure rules) + automation-control maturity (P1-P4)

`run_local_eval.py` no longer hard-codes pure rules; it is driven by **capability_probe (environment probe) + runtime_controller (strategy decision) + the config-environment-performance LUT (data-driven)**
to auto-select the current-environment-optimal config (startup prints `strategy=...` and `lut=...`):

| Environment | Chosen default strategy | Public-200 sessions (current default config) |
|---|---|---|
| BLaIR available (offline npy + transformers) | `strategy=hybrid_rule` + LUT `fingerprint_combo` | **1.0 HR / 0.9364 MRR / 2.33 MTTC / 0.9543 TS** |
| No BLaIR (pure-rule baseline) | `strategy=bm25_rule` + LUT `rule_bm25` | fingerprint/gating still apply (same column) |
| LLM available (key) + rewrite signal | `intent=llm` (cascaded fallback / rewrite-guard dynamic upgrade) | public templates unchanged (safe) |
| Rerank model (bge/Rex) enabled | second opinion only in `recover` mode | slight drop (off by default, optional) |

Key design (all public-200 A/B validated):
1. **Main improvement chain**: constraint-combination fingerprint (exact catalog count) + combo_bonus (super-linear full-hit bonus) + output gating
   (low-confidence hold-back, early full release on high confidence) push the target up -> MRR 0.64->0.94, TS 0.88->0.95 (see the optimization record below).
2. **BLaIR dense only in recover mode** (`retrieval_backend=auto`): on the public set recover almost never triggers -> dense sleeps, zero loss;
   hard-constraint re-check + 0.5 weight make it a safe semantic-recall net for private-set miss streaks.
3. **Rerank models off by default**: full/recover usage both slightly hurt (A/B proven); kept as `RERANKER_MODEL_ENABLE=1` opt-in.
4. **LLM intent off by default, auto-enabled when the environment allows**: cascaded (rules first, LLM only on low confidence), no-key env falls back to rules.

**Automation-control maturity (P1-P4, product-grade)**:
- **P1 closed-loop degradation**: startup selection via the LUT (`utils/lut.py` + `RuntimeController.decide()`, missing LUT -> default);
  runtime phase circuit breakers (`utils/circuit_breaker.py`: dense/reranker degrade on consecutive failures, hybrid->bm25 / rerank->rule);
  rewrite guard (`agent/rewrite_guard.py`: signals like consecutive "disclosure but zero new constraints" -> upgrade to LLM intent on the spot).
- **P2 observability**: per-session structured logs (strategy/latency/tokens/phase_timings/degradation/reasons) aggregated into results.json
  (`agent/main_agent.py::_record_session_log`).
- **P3 config-as-data**: `config/profiles.py` CONFIG_PROFILES is the single source of truth, shared and validated by build_lut and the controller.
- **P4 cost/latency disclosure**: the LUT contains measured latency (3-run median) and cost_usd_per_session; README references
  `data/assets/env_config_lut.json` as the required "model/cost/latency/token/fallback" disclosure document.

LUT rebuild: `python scripts/build_lut.py` (16 environment fingerprints x 5 config profiles, n_samples=200 full; deduped scores, ~40-60min).

## combo_bonus: super-linear bonus for full multi-constraint hits (raises MRR)

**Insight**: the hidden target comes from a real purchase, so the intent-card constraints are generated from that product's own metadata -- the target text
**satisfies all disclosed constraints**; distractors usually "hit in pieces" (each satisfying only part). Coverage is a per-item weighted average
(a linear signal) and cannot tell "1 product fully hits" from "3 products each hit one".

**Design** (`agent/reranker.py::_rule_score`):
- count the weighted number of "fully hit" constraints `full_count` (hard=1.0, soft=0.5; `hit>=0.999` counts as full);
- `combo_norm = C(full_count,2) / C(full_denom,2)` -- the share of "satisfied constraint pairs", triggering only at >=2 hits;
  full hit = 1.0, naturally super-linear;
- `score += W_COMBO x combo_norm` (default 0.10; env `COMBO_BONUS_WEIGHT` tunable).

**A/B (public 200 sessions)** (historical; see the current-state note below):
| Config | HR@10 | MRR | MTTC | TS |
|---|---|---|---|---|
| no combo (previous default) | 1.0 | 0.6438 | 1.72 | 0.8787 |
| **+ combo_bonus** | 1.0 | **0.6486** | 1.72 | **0.8802** |

> **Current state (default config)**: combo_bonus is in the default (W_COMBO=0.10); with the constraint fingerprint + output gating stacked,
> the full public-200 result is **MRR 0.9364 / TS 0.9543**; the table above is the historical A/B when combo was introduced.
- Gains concentrate in **buying** (MRR +0.012; strong hard constraints, full target hits);
- weights 0.05-0.30 give the same result (saturated, robust); hard-only counting is ineffective (a target with 1 hard cannot trigger C(1,2)=0,
  **soft counting is the key** -- a target = 1 hard + multiple soft full hits).

## Constraint-combination fingerprint (exact catalog count)

**Insight**: the hidden target satisfies all disclosed constraints; the "number of products satisfying all constraints" (combination rarity) is a stronger
confidence signal -- the smaller the count, the more the combination locks onto the target.

**Design** (`agent/reranker.py`):
- `_fingerprint(retriever, active)`: **exact catalog count** of products satisfying all active constraints (hard+soft, `phrase_exists` full-hit rule)
  + the satisfying set; cached by constraint key with a lazily built index (no repeated full-catalog scans);
- tiered bonus (only for candidates in the full-satisfier set): `count==1` top (+1.0) / `count<=10` (+0.5) / `count<=50` (+0.2);
  no bonus for `count>50` (over-general constraints) -- **confidence gating**;
- switch: `COMBO_FINGERPRINT_ENABLE=1` enables it, **on by default** (default.json `fingerprint.enable=true`; `COMBO_FINGERPRINT_ENABLE=0` disables);
  bonuses tunable via `COMBO_FINGERPRINT_BONUS_UNIQUE/TEN/FIFTY`.

**A/B (public 200 sessions)** (historical):
| Config | HR@10 | MRR | MTTC | TS |
|---|---|---|---|---|
| fingerprint off (then-default, historical) | 1.0 | 0.6486 | 1.72 | 0.8802 |
| **fingerprint on** | 1.0 | **0.6520** | 1.72 | **0.8812** |

- with combo_bonus stacked: MRR 0.6438 -> 0.6520, TS 0.8787 -> 0.8812 (browsing +0.008 extra);
- bonus magnitude 0.5-1.5 gives the same result (saturated, robust -- the bonus is equal for all intersection members and only lifts the
  "full-vs-partial" boundary);
- **Current state (default config)**: fingerprint on by default; stacked with combo_bonus + output gating, the full public-200 result is
  **MRR 0.9364 / TS 0.9543** (the table above is the historical A/B when it was introduced).

## Local Web Demo

```bash
pip install -r requirements-web.txt
LLM_PROVIDER=none python -m webapp
# custom participant-kit catalog:
LLM_PROVIDER=none python -m webapp --catalog /path/to/catalog.jsonl --port 8080
```

The default catalog path is `data/catalog.jsonl`; use `--catalog` to select a participant-kit
catalog at another path. The demo binds locally to `http://127.0.0.1:8000` by default (or the
chosen local port), serves no external assets, and returns ordinary non-streaming responses.

Chats persist only in the browser while the page remains available: refresh can recover the
current chat, while restarting the service resets its in-memory sessions. The frontend does not
impose a turn cap. It runs the existing Agent pipeline and retains its automatic existing-model
fallback behavior; `LLM_PROVIDER=none` keeps the demo offline.
